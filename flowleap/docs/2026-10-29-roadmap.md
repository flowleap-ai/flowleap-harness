## What v1 still lacks

### For a firm to trust it (security)

- **Vault and key entry in the browser (#31).** Office keys and the FlowLeap token are still in the runtime's keys document. Invariant `keys.none-in-runtime` is partial.
- **Web gate (#33).** A runtime can reach the internet directly. Invariants `network.no-direct-internet` and `network.offline-chat-no-outbound` are not proved.
- **Audit trail (#35).** No firm-wide record of who did what.
- **Spawner robustness (#48).** One broken runtime can delay another attorney's wake.
- **Two attorneys and a budget stop in the gate (#38).**

### For a firm to run it (administration)

- **Admin console (#34).** Today budgets, users and keys need `install.sh` on the server.
- **Budget request (#89).** An attorney at 100 % has no way to ask for more.
- **The stable channel.** "stable" is still `2026.10.26.1534`; its gate (FTO and prior art, about 4 to 6M tokens) needs the founder.

### For an attorney to use it every day (product)

- **Real data on the dashboard (#60):** Coming up, budget, activity; deep links; ⌘K.
- **Real data on the office action board (#81):** the board reads the #46 result file; state and owner kept; Export Word.
- **The skill pack on the firm:** a flowleap-cli release with #46, then a runtime release, then `SKILLS=pack` on the test firm.
- **Firm skills library (#71).** In v1 scope; not started.
- **Knowledge v1:** cases, notes with links, search, graph view (OS-2, OS-3 of the scope's order). Not started; no ticket yet.

### Before prospects see it (polish)

- **Hide DeepSeek/DSH names and developer pages (#84)**, and plugin creation (#70).
- **Connectors wizard bug (#79).**

## Proposed order

| Phase | Goal | Work | Size |
|---|---|---|---|
| A. Close the loop (now) | What exists is real, not sample | #81 and #60 data steps; the skill pack chain on the test firm; close the finished tickets | 1 to 2 weeks |
| B. Pilot-ready | A first firm can run it without the founder on the server | #84, #70, #79; #34 admin console with #89 and the Paperclip ideas (one approval queue, one budget request per month); #48; the stable gate | 2 to 3 weeks |
| C. Trust | The security invariants that a law firm asks about are proved | #31 vault, #33 web gate, #35 audit trail, #38 in the gate | 3 to 4 weeks |
| D. Firm knowledge | The firm's own know-how in the agents | #71 firm skills library; Knowledge v1 (cases, notes, graph), with the research ideas: facts with source and validity dates, an embedding model lock, a German-capable local embedder | 3 to 5 weeks |
| E. Ways in (Later list) | Attorneys reach it from their own tools | #77 MCP door, #75 desktop client, #76 phone | after D |

Phases B and C can overlap: B is mostly Web UI, C is mostly flowleap-os and the network.

## Ideas from the 2026-10-29 research

- **Paperclip:** an automatic budget request at the 100 % stop (one per month); one approval object and queue for every human decision; cost per chat, routine run and agent, with "unknown" in place of $0; routine overlap and catch-up rules; one owner and review stages per work item, and a responsible user in each audit record.
- **supermemory and MemPalace:** neither replaces the Knowledge Pool design. Ideas: facts with source and validity dates, contradictions kept side by side; an embedding model lock; a local multilingual embedder; an ingestion queue with a memory cap; a read-only mode.

## Decisions (2026-10-29)

1. **Pilot-ready is phases A to C.** Knowledge (D) starts after the first pilot firm starts, so that the pilot's work shapes the Knowledge Pool.
2. **B and C run in parallel.** B is mostly Web UI; C is mostly flowleap-os and the network.
3. **The MCP door (#77) stays after C.** It opens the firm's data to outside AI tools, so the web gate and the audit trail come first.
4. **The first pilot firm sets the dates.** The founder names a target firm; the phases are then planned back from its start date. Until then, the sizes in "Proposed order" are the plan.
